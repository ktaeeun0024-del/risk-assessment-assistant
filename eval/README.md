# 검증 측정 (AI ③)

"이 도구가 만든 평가표가 공공 표준모델의 위험요인을 얼마나 찾아내는가"를 숫자로 잰다. 비용 0원, AI 채점 없음.

## 파일

| 파일 | 내용 |
| --- | --- |
| `cases.json` | 입력: 표준모델 작업 20종을 반장이 말로 설명하듯 쓴 작업 설명 (위험 단어는 넣지 않음) |
| `build-set.mts` | `cases.json` + 표준모델 → `eval_set.json` (정답 위험요인, 검색에서 뺄 파일) |
| `eval_set.json` | 검증 세트: 20종, 정답 위험요인 359개 |
| `match.ts` | 채점 규칙 (같은 위험요인인지 판단, 재현율 계산) |
| `run.mts` | 측정: 실제 서비스와 같은 순서(검색 초안 → AI 초안 → 검사기)로 돌린다 |
| `review.mts` | 사람 판정: 자동 채점이 놓치거나 잘못 짝지은 것을 사람이 바로잡아 다시 계산한다 |
| `results/` | 측정별 상세 결과 (git에 올리지 않음) |
| `reviews/` | 사람이 채운 판정지 사본 (git에 남김) |

## 실행

```bash
npm run eval:build                                   # cases.json을 고쳤을 때만
npm run eval -- --mode search                        # 검색 초안 (기준선, AI 없음)
npm run eval -- --mode ai --model 모델ID:free --cases E01,E02,E03,E04,E05,E06,E07,E08,E09,E10
npm run eval -- --mode ai --model 모델ID:free --cases E11,E12,E13,E14,E15,E16,E17,E18,E19,E20
```

무료 모델은 하루 50회(크레딧을 산 적 없을 때), 1분 20회 한도가 있다. 작업 하나에 AI 호출이 1~3번이라 **10종씩 나눠** 돌린다.

## 측정 규칙

- **누수 방지**: 정답은 표준모델 원본 파일에서 나오는데, 검색 초안과 AI 참고 자료도 표준모델을 검색한다. 그대로 재면 정답을 검색으로 가져오게 되므로, 측정 때는 평가 대상 원본 파일과 그 복사본(정답 문장을 40% 이상 그대로 가진 파일)을 검색에서 뺀다. "처음 보는 작업"에서의 실력을 재는 셈이다.
- **정답 정리**: 원본 파일의 유해·위험요인에서 거의 같은 문장(겹침 0.8 이상)은 하나로 합친다.
- **위험요인 재현율**: 정답 위험요인 중 초안에 있는 비율. 1:1로 짝짓는다(초안 한 줄이 정답 여러 개를 동시에 맞힐 수 없음). 같은 위험요인 기준:
  1. 사고 유형(끼임·떨어짐·감전 … 18가지)이 같고, 유형 말을 뺀 대상·원인 글자 조각이 20% 이상 겹침
  2. 또는 글자 조각이 60% 이상 겹침(거의 같은 문장)
- **사고 유형 재현율**: 정답에 나온 사고 유형 중 초안에도 나온 비율. 말이 달라도 덜 흔들리는 보조 지표.
- **초안 중 정답과 겹친 비율**: 나머지가 틀렸다는 뜻은 아니다(정답에 없는 위험을 더 찾았을 수 있음).
- 검사기 통과율, 항목 수, 1건당 시간도 함께 적는다. AI가 실패한 작업은 "실패 포함 재현율"에서 0점으로 센다.

## 사람 판정 (자동 채점 보정)

자동 채점은 글자가 겹치는지만 봐서 '칼에 손 베임' ↔ '칼날에 베임 위험'처럼 말이 다르면 놓치고, 사고 유형만 같고 원인이 다른 짝('증기에 화상' ↔ '손잡이에 화상')을 맞혔다고 하기도 한다. 그래서 AI 측정마다 사람이 판정지를 한 번 확인한다.

```bash
npm run eval:review -- eval/results/<측정결과>.json            # 판정지 <측정결과>.review.json 만들기
npm run eval:review -- --apply eval/results/<측정결과>.review.json   # 판정 반영해 다시 계산
```

판정지에서 채울 칸:

| 칸 | 할 일 |
| --- | --- |
| 자동짝 | 자동 채점이 맞혔다고 한 짝. 같은 위험이 아니면 `맞음` → `틀림`, 다른 초안이 그 정답과 같은 위험이면 그 초안 번호 (짝 바꾸기) |
| 놓친정답 | 같은 뜻의 초안이 있으면 그 초안 번호, 없으면 `없음` (후보 3개를 겹침 순으로 보여 줌) |
| 초안판정 | 모든 초안 목록. 최종적으로 정답과 짝이 안 된 초안만 `맞는 위험`(정답엔 없지만 실제로 있을 만한 위험) / `틀림` / `중복` (짝지은 초안은 비워 둠) |

계산 결과로 보고하는 숫자:
- **사람 판정 재현율**: 정답 중 (자동짝 `맞음` + 사람이 번호를 적은 놓친정답)의 비율. 포스터에는 자동 재현율과 함께 적는다.
- **쓸 만한 초안 비율**: 초안 중 정답과 짝지어졌거나 `맞는 위험`인 항목의 비율. 재현율이 낮아도 초안이 틀린 것은 아님을 보여 준다.
- **채점기 확인**: 자동짝 중 `틀림` 수, 놓쳤다고 한 정답 중 실제로 초안에 있던 수.

판정지는 `results/`에 만들어지고, 다 채우면 `reviews/`에 복사해 git에 남긴다. 최종 숫자는 아래 결과 기록 표에 옮긴다.

## 재현율을 읽는 법

재현율 41%는 "59%가 틀렸다"가 아니라 "정답 목록 중 41%를 찾았다"는 뜻이다. 낮게 나오는 이유:
1. 자동 채점이 같은 뜻의 다른 말을 놓친다 → 사람 판정으로 보정
2. 정답은 가스공사 표준모델 한 곳의 의견이다. 정답에 없는 위험(예: 드릴 비트에 장갑이 말림)을 찾아도 점수에 안 들어간다 → 쓸 만한 초안 비율로 따로 본다
3. AI는 위험을 10개 안팎으로 추리는데 정답은 13~14개라 다 맞혀도 100%가 안 된다

11/15 ultra 시험에서 정답과 짝이 안 된 초안 10개를 읽어 보니 모두 실제로 있을 만한 위험이었다(감전, 드릴에 말림, 칼 베임, 기름 화재 등). 그래서 이 도구는 "AI가 초안을 만들고 사람이 빠진 것을 채우는" 방식으로 쓴다.

- 20종 중 5종(E04·E11·E12·E13·E17)은 AI를 2~3번 불러(형식 오류 재요청 또는 검사 오류 수정) 190~230초가 걸렸다. 배포 사이트의 Supabase 함수는 135초 안에 끝내야 하므로, 이런 경우 첫 답이 형식에 맞으면 검사 오류 수정 없이 그대로 보여 주고, 첫 답의 형식이 틀리면 검색 초안으로 대체된다.
- 검색 초안은 비슷한 작업의 표준모델이 있으면 잘 맞고(E18 실내 청소 33%), 없으면 거의 못 찾는다(E11·E12 수소 설비 0%). AI는 같은 작업에서 40~50%.

## 프롬프트 개선 (11/17, draft-v1 → v3)

20종 검증에서 드러난 문제를 고치고, 문제가 있던 작업만 다시 쟀다 (자동 채점, 같은 무료 모델).

| 문제 | 고친 것 |
| --- | --- |
| 설명에 없는 설비·약품을 지어냄 (비계에 그라인더 등) | 맨 위 "가장 중요한 규칙"으로: 설명에 나온 기계·공구·물질만, 참고 자료에 있어도 설명에 없으면 쓰지 않기 |
| 원인 없이 결과만 쓴 흐린 문장 | 좋은 예·나쁜 예, 한 문장에 사고 하나, 대상(기계·작업)과 원인 필수 |
| 자주 놓친 관리적 원인 | 보호구 미착용·혼자 작업·신호수 없음 등을 구체적인 사고와 묶어 쓰기 (v2에서 따로 쓰게 했더니 '단독 작업으로 초기 대응 지연' 같은 일반론이 생겨 v3에서 고침) |
| "형식 오류"로 다시 부름 | 원인은 형식이 아니라 **빈 답**이었다(틀린 답 3개가 모두 0바이트). 답이 길어 100초를 넘기면 빈 답이 오는 것으로 보여 항목 10~13개·대책 1~2개로 줄임. 코드도 코드 블록·끝 쉼표·잘린 답을 너그럽게 읽게 함 |
| 한자·일본어가 섞임 ('사용済 필터') | 프롬프트에서 금지 + 검사기 경고 추가 |

| --- | --- | --- | --- |
| 빈 답으로 다시 부름 | 4/5 | 3/5 | 1/5 |
| 1건 평균 시간 | 약 200초 | 159초 | 127초 |
| 135초 안에 끝남 (배포 사이트 제한) | 1/5 | 2/5 | 4/5 |
| 위험요인 재현율 (자동) | 28% | 38% | 35% |

- v3 마지막 수정 후 4종(E02·E12·E13·E17) 다시 재기: 4종 모두 1번 호출, 67~115초, 빈 답 없음.
- '40자 안팎으로 짧게'를 넣었더니 E17에서 "허리에 무리가 가 요통 발생"처럼 대상·원인이 빠진 문장만 나와(재현율 6%) 빼고, 대상·원인 필수 규칙으로 바꿈 → 16%로 회복.
- 생각 양을 '낮음'으로 줄이면 빠르지만(110초) 재현율이 떨어져(27%, E12 0%) 쓰지 않는다. 번역은 생각을 끈다(판단이 필요 없음).
- 형식이 틀린(빈) 답은 측정할 때 `results/raw/`에 저장된다.

- **재현율은 그대로다** (32.0% → 30.8%, 작업마다 ±10%p 안에서 오르내림). v3는 지어낸 설비·흐린 문장을 줄였지만(틀린 초안 3개, E05 '몰탈·벽돌' 1개 포함) 찾는 위험의 양은 늘지 않았다.
- **"빈 답"의 진짜 원인은 우리 코드의 시간 제한이었다.** E02의 빈 답 두 번은 간격이 정확히 120.0초였고, 다른 빈 답도 모두 호출 120초 뒤에 났다. OpenRouter는 답을 다 만들기 전에 응답 머리(HTTP 200)를 먼저 보내므로 `fetch`는 성공하고, 본문을 읽는 도중 `AbortSignal.timeout`(측정은 120초)이 끊는다. 그런데 `res.json().catch(() => null)`이 이 시간 초과를 삼켜 **빈 답·형식 오류처럼 보였다.** 11/17에 "답이 길면 위에서 끊긴다"고 본 것은 틀린 추측이다. 답 길이를 줄여 빨라진 효과는 있지만, 그날 무료 모델 서버가 느리면(11/18) 다시 120초를 넘긴다.
- 그래서 11/17 5종 시험의 "다시 부름 4/5 → 1/5"는 프롬프트 효과와 그날 서버 속도가 섞인 숫자다.
- 2일차(E11~E20)는 측정 조건을 같게 하려고 코드를 그대로 두고 잰다. 시간 초과를 제대로 알리는 수정(본문 읽기 시간 초과 → "AI 응답이 너무 오래 걸려요")은 측정이 끝난 뒤에 한다.

## 채점기 정확도 (2026-11-15, 검색 초안 결과 표본 확인)

- 맞혔다고 한 짝 20개 중 16개가 실제로 같은 위험요인 (**80%**). 틀린 4개는 사고 유형은 같지만 원인이 다른 경우.
- 놓쳤다고 한 정답 20개 중 2개는 초안에 같은 뜻의 항목이 있었음 (**10%**). 말이 아주 다른 경우(예: '방사선 피폭' ↔ '방사능 노출').
- 오차가 양쪽으로 있어 **같은 채점기로 두 방식을 비교하는 것은 유효**하지만, 절대값에는 몇 %p 오차가 있다. 포스터에는 "자동 채점, 표본 확인 정확도 약 80~90%"를 함께 적는다.
